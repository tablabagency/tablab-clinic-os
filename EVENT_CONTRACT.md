## 1. Canonical event envelope (revised)

```json
{
  "event_id": "uuid-v4, generated by producer, globally unique",
  "event_type": "lead.created | lead.updated | qualification.updated | followup.scheduled | followup.sent | booking.created | booking.cancelled | booking.rescheduled | handover.required | system.failure",
  "event_version": "1.0",
  "source": "manychat | cal.com | n8n-internal | openai-classifier",
  "clinic_id": "string, required",
  "occurred_at": "ISO 8601 — authoritative business time, from the source system",
  "ingested_at": "ISO 8601 — REQUIRED as of v0.2 (was recommended-only in v0.1). Set by n8n at receipt time.",
  "external_id": "the source system's own ID for this event/object",
  "lead_id": "internal lead_id, present where applicable",
  "payload": { "event-type-specific fields" }
}
```

**Change from v0.1:** `ingested_at` moves from "recommended addition" to a
**required** field. Rationale (item B): without it, the ordering rules in
§2 and the crash-recovery timeout in §6.5 have no basis to measure against
— it stopped being optional the moment those two features were designed.

## 2. Event ordering rules (new section — addresses item B)

These rules govern how n8n applies any state-changing event, and mirror
DATA_MODEL.md §8.

1. **Primary ordering key:** the tuple `(occurred_at, ingested_at,
   event_id)`, compared against the record's stored
   `(last_event_occurred_at, last_event_ingested_at, last_event_id)` —
   **not** against `updated_at` alone (v0.4 correction: `updated_at` only
   stores the winning `occurred_at` value, which is not enough information
   to correctly re-evaluate a replayed event that previously lost a tie —
   see DATA_MODEL.md §8 for the full rationale). An event is only applied
   to the record's state-changing fields if its tuple sorts after the
   record's stored tuple, per the tie-break order in rule 3.
2. **Out-of-order handling:** an event that fails rule 1 is **not**
   silently applied and **not** silently dropped — it is logged (a
   lightweight log entry, not necessarily a full `system.failure`, since
   out-of-order delivery is expected/normal in a distributed system, not
   itself a fault) and discarded from a state-mutation perspective. The
   record's ordering metadata is left unchanged.
3. **Tie-break:** equal `occurred_at` → order by `ingested_at`. Equal on
   both (rare) → order by `event_id` lexical order. This is a
   last-resort deterministic rule, not expected to matter at V1 volume.
4. **Clock-skew tolerance (RECOMMENDATION):** reject (route to
   `system.failure`) any event whose `occurred_at` is implausibly far in
   the future relative to `ingested_at` (exact threshold is an
   implementation detail, e.g. 5 minutes) rather than trusting it.
5. **Write rule (revised in v0.4):** every successful state-changing apply
   sets, as one unit: `updated_at = incoming event's occurred_at`
   (unchanged — remains a business-time field, kept for human/dashboard
   readability), **and** `last_event_occurred_at` /
   `last_event_ingested_at` / `last_event_id` = the applied event's
   corresponding values (new — this is what makes rule 1 actually
   enforceable on the next event, which `updated_at` alone could not do).

## 3. Contact vs. conversation identity in events (new section — addresses item A)

Two distinct identities now flow through events, and they must not be
conflated (this was the root problem in v0.1):

- **Conversation identity** — `external_id` on `lead.created` /
  `lead.updated` (the Manychat conversation/subscriber ID). Used **only**
  for webhook-replay idempotency (§6.1) — i.e. "have I already processed
  this exact conversation-creation webhook."
- **Contact identity** — resolved separately, from `payload.email` /
  `payload.phone` if present, against the `Contacts` table
  (DATA_MODEL.md §2), **scoped within `clinic_id`**. This determines
  "which person is this," independent of which channel/conversation they
  used.

A single `lead.created` event therefore does two independent things in
n8n: (1) idempotent conversation-thread dedupe using `external_id`, and
(2) best-effort contact matching/creation using `payload.email`/`phone`.
Failure or ambiguity in (2) must never block or corrupt (1) — a lead
record is always created (or matched to an existing one) even if contact
resolution results in an `UNRESOLVED` contact.

## 4. System boundary definitions (unchanged from v0.1)

- **Manychat** owns: conversation UI/UX, normal-conversation AI replies
  (decision #1), native channel message history. Emits events into n8n;
  never reads `lifecycle_stage` back.
- **n8n** owns: event translation, validation, idempotency, ordering
  (§2), contact/conversation resolution (§3), `lifecycle_stage`
  transitions (sole writer), booking lineage resolution (§7),
  retry/failure handling, orchestration.
- **Airtable** owns: persistence and presentation. No Airtable automation
  independently mutates `lifecycle_stage` or booking lineage.
- **Cal.com** owns: booking source of truth (decision #7) — but as of
  v0.2, "source of truth" is interpreted at the level of *what actually
  happened to the appointment*, while `booking_id` (the stable internal
  identity) and its UID lineage are TabLab's own bookkeeping on top of
  that truth — see §7.
- **OpenAI** owns: structured intelligence only (decision #2). No
  conversation state. Low-confidence fallback is human handover
  (decision #5), never a second AI attempt (decision #3).

## 5. Event definitions

### 5.1 `lead.created` (revised — item A)

| | |
|---|---|
| **Required fields** | `clinic_id`, `external_id` (conversation ID), `payload.channel`, `payload.source`; `payload.email`/`payload.phone` optional, used for contact matching only |
| **Idempotency key** | `(clinic_id, external_id, channel)` — **conversation-thread dedupe only**, per §3 |
| **Contact resolution (separate step, not part of the idempotency key)** | Normalise `payload.email`/`payload.phone` (trim+lowercase / E.164 — DATA_MODEL.md §2), then match against `Contacts` within `clinic_id`. Match → link `contact_id`, `match_confidence = MATCHED` (v0.3: renamed from `CONFIRMED`). No match → create new `Contacts` row, `match_confidence = UNRESOLVED` — **subject to the concurrency-safety requirement in DATA_MODEL.md §2** (search-then-create is not atomic; a collision recheck or serialising mechanism is required so two near-simultaneous `lead.created` events for the same person cannot both create a contact) |
| **Producer** | n8n, translating a Manychat inbound webhook |
| **Consumer** | Airtable (`Leads`, `Contacts`) |
| **Expected behaviour** | Create one `Leads` record (`lifecycle_stage = NEW`), linked to a resolved-or-new `Contacts` record |
| **Duplicate handling** | Upsert against the conversation-thread idempotency key. Contact resolution is independently idempotent (matching the same email/phone twice yields the same `contact_id`, never a second contact row for an exact match) |
| **Failure handling** | Standard retry/backoff/alert (unchanged from v0.1) |

### 5.2 `lead.updated` (ordering wording corrected in v0.4)

|---|---|
| **Required fields** | `clinic_id`, `lead_id`, `payload` (changed fields only) |

(v0.4 correction: this row previously read "apply only if `occurred_at >= record.updated_at`," which contradicted §2's tuple-based rule — that wording is removed.) |

### 5.5 `followup.sent` (rewritten — item C)

**This event now represents a claim, not a completed action.** The actual
completion is a state machine, not a single event/write.

| | |
|---|---|
| **Trigger** | Dispatcher identifies a due `Follow_ups` row with `status = SCHEDULED` |
| **Step 1 — Claim** | Conditional write: `status: SCHEDULED → SENDING`, only succeeds if current status is still `SCHEDULED` (this is itself the idempotency mechanism preventing two concurrent dispatcher runs from both sending — a compare-and-swap, not a plain update) |
| **Step 2 — Precondition re-check** | Re-verify `lead.follow_up_active` and current `lifecycle_stage`. Fails → `status: SENDING → SKIPPED`, `skip_reason` set, **no message sent** |
| **Step 3 — Send** | Call the channel (Manychat) send API. Capture `provider_message_id` from the response, **if the provider returns one — this is provider-dependent and not guaranteed; its absence is an expected, normal outcome, not an implementation bug** |
| **Step 4 — Confirm** | `status: SENDING → SENT`, `sent_at` set, `provider_message_id` stored if available |
| **Idempotency key** | `follow_up_id`, but the meaningful protection is the Step 1 compare-and-swap, not just a key check on final write |
| **The crash window this closes** | If the process dies between Step 3 (message physically sent) and Step 4 (state confirmed), the row is left in `SENDING` — **visible and actionable**, instead of silently reverting to `SCHEDULED` (which would risk a duplicate send) or silently being assumed `SENT` (which would risk masking a real failure) |
| **Reconciliation (a separate, scheduled n8n check, not part of the dispatch flow itself)** | Any `Follow_ups` row in `SENDING` for longer than a timeout (DATA_MODEL.md §5.1 — exact duration TBD, flagged as open item): if `provider_message_id` is present, query the channel API to confirm delivery → `SENT` retroactively if confirmed. **If `provider_message_id` was never captured — which is an expected, provider-dependent outcome, not a fault — or if the provider query is inconclusive,** → `SEND_UNCERTAIN`, `system.failure` logged, alert raised, and — critically — **`follow_up_active` is set false and `handover_required` may be set true** for that lead so no further automation touches it until a human resolves the ambiguity |
| **Producer** | n8n dispatcher (Steps 1–4) and a separate n8n reconciliation job (timeout handling) |
| **Consumer** | Airtable (`Follow_ups`) |
| **Failure handling** | As described above — this event's failure handling *is* the crash-safety design, not a bolt-on retry policy |

### 5.6 `booking.created` (rewritten — item D)

| | |
|---|---|
| **Required fields** | `clinic_id`, `external_id` = incoming Cal.com booking UID, `lead_id`, `payload.appointment_at` |
| **Resolution step (new — see §7 for the full algorithm)** | Before writing anything, n8n checks `Booking_UID_History` for `(clinic_id, cal_uid)` — **corrected in v0.3: the lookup is always scoped by `clinic_id`, never `cal_uid` alone** (see DATA_MODEL.md §4.2). Not found → this is genuinely new: create a new `booking_id`, write `Bookings` row, write a `Booking_UID_History` row with `event_type = CREATED` |
| **Idempotency key** | `(clinic_id, cal_uid)` lookup against `Booking_UID_History` (unique constraint there, DATA_MODEL.md §4.2) — if the UID is already known for this clinic, this is a duplicate delivery of the same creation event, not a new booking; no-op on the `Bookings`/history write, though `lead.lifecycle_stage` transition (below) still needs to be idempotent-safe (setting `BOOKED` twice is harmless) |
| **Consumer** | Airtable (`Bookings.status = CONFIRMED`, `Booking_UID_History`); `Leads.lifecycle_stage → BOOKED` (v0.4: `BOOKED` now specifically means "has an active/confirmed appointment," i.e. tracks `Bookings.status = CONFIRMED` — see DATA_MODEL.md §6); `Leads.follow_up_active → false` |
| **Orchestration guarantee (reworded in v0.3 — was "same transaction," which overstated what Airtable/n8n can actually guarantee):** n8n processes this event as **one orchestration unit** — the `Bookings`/`Booking_UID_History` write, the `lifecycle_stage` update, and the follow-up-stop update are performed in a defined order within a single n8n execution, with recovery/reconciliation (per the standard failure-handling pattern, §5.10) if any individual downstream write fails partway through. This is not a database transaction with atomic rollback — Airtable doesn't offer one — so the design must tolerate a partial-completion state (e.g. `Bookings` written but `lifecycle_stage` update failed) via retry and, on exhaustion, `system.failure` + alert, rather than assuming all-or-nothing behaviour. |
| **Failure handling** | Standard retry/alert; "no silent loss" applies as before |

### 5.7 `booking.rescheduled` (unblocked — item D)

| | |
|---|---|
| **Required fields** | `clinic_id`, `external_id` = the new Cal.com UID, `payload.new_appointment_at`, and — **if Cal.com's webhook provides it** — a reference to the previous UID (commonly a `rescheduleUid`/`fromReschedule`-style field; exact field name to be confirmed against Cal.com's actual payload during implementation) |
| **Resolution step (see §7)** | (a) If the payload includes a previous-UID reference → look it up in `Booking_UID_History` **scoped to `(clinic_id, cal_uid)`**, resolve to the existing `booking_id`, append a new history row (`RESCHEDULED_FROM` on the old UID, `RESCHEDULED_TO` on the new one), update `Bookings.current_cal_uid` and `appointment_at` on the **same** `booking_id`. (b) If no previous-UID reference is available, and the new `external_id` doesn't match anything in history for this clinic → **do not guess.** Route to `system.failure` / manual reconciliation rather than either silently creating a duplicate booking or silently discarding the event. |
| **Idempotency key** | `(clinic_id, new cal_uid)` — once resolved and written to history, a redelivery of the same reschedule event is recognised as already-known (found in `Booking_UID_History`) and is a no-op |
| **Consumer** | Airtable (`Bookings`, `Booking_UID_History`). `Bookings.status` is **not** touched by a reschedule (v0.4: `RESCHEDULED` was removed from the status enum — see DATA_MODEL.md §4.1); it remains `CONFIRMED` throughout, since the lineage table, not the status field, is what represents the reschedule. |
| **This is no longer a hard blocker for build** — it was in v0.1 because the design assumed one behaviour. v0.2's fallback path (case b above) means implementation can proceed now, with Cal.com's exact payload shape confirmed empirically during TEST-005/TEST-006 rather than needing to be known in advance. |

### 5.8 `booking.cancelled` (unchanged mechanism, key updated)

|---|---|
| **Required fields** | `clinic_id`, `external_id` = `cal_uid` |
| **Resolution** | Look up `(clinic_id, cal_uid)` in `Booking_UID_History` → resolve `booking_id` → update `Bookings.status = CANCELLED` |

## 6. Booking UID resolution algorithm (new section — addresses item D directly)

Explicit pseudocode-level description, since this is the crux of the fix:

```
on booking event with clinic_id and external_id = incoming_uid:

  1. look up (clinic_id, incoming_uid) in Booking_UID_History
     -- corrected in v0.3: lookup is always scoped by clinic_id;
     -- a bare incoming_uid lookup would violate multi-clinic isolation
  2. if found:
       booking_id = the linked booking_id
       proceed as an update to that booking_id (idempotent — this event
       has been seen before in some form, or is a legitimate
       state-transition on a known booking)
  3. if not found AND event_type == booking.created:
       this is genuinely new — create booking_id, write history row
       (event_type = CREATED)
  4. if not found AND event_type == booking.rescheduled:
       a. if payload carries a previous-UID reference:
            look up (clinic_id, previous UID) in history
            if found: resolve to its booking_id, append new history row,
                      update Bookings.current_cal_uid
            if not found: fall through to (b) — the referenced previous
            UID is itself unknown, which is itself worth logging
       b. if no usable previous-UID reference, or (a) fell through:
            do NOT create a new booking_id silently
            do NOT discard the event silently
            → system.failure + handover.required, manual reconciliation
  5. if not found AND event_type == booking.cancelled:
       an unknown UID being cancelled is itself an anomaly
       → system.failure, do not guess which booking it refers to
```

**This algorithm is the concrete mechanism that lets §5.7's "no longer a
hard blocker" claim hold** — every branch has a defined, safe outcome,
including the branches where Cal.com's actual behaviour turns out to be
something other than what's assumed.
